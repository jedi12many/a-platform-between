# The Commodore 64 build

*Milestone E4. What's here runs The Fare from a 1541 disk image, with pictures.*

## Playing it

`make c64` writes `build/the-fare.d64`, `build/eighteen-minutes.d64`
(*Eighteen Minutes*, Departure 01) and `build/deep-yards.d64` (the Deep Yards, E7). In VICE (or on a real C64 with the image on an
SD2IEC or a real floppy):

```
LOAD"APB",8
RUN
```

Pick **1** to board and type your Passport, a line at a time (RETURN after each, then a
blank line), and a Boarding Pass or a blank line. From then on it's menus: press the
number. At a story menu, **S** saves the trip to the disk; next time, pick **2** at the
start to carry on. A border that turns grey or green means the disk is working.

## How it fits in 64 KB

BASIC is switched out, so a program has $0801 to $CFFF, about 51 KB. The game itself
(the VM, the battle engine, the rules core, the boarding desk) is 38 KB of 6502 code
before a Departure is even loaded, so it's split the way C64 games always were: a main
program that stays, and **overlays**, code that loads from the disk into one shared
area only when it's needed.

| Address | What | Size |
|---|---|---|
| $0801 | the main program: the VM's interpreter, the rules, the C64 front end, the status and check lines, the raster split | 22 KB |
| after it | buffers: the depot, the battle's state, the sprites' plan | 7 KB |
| below $7BF0 | the C stack (the deepest route uses about 115 bytes; `make test-c64` fails a run that uses more than 384) | 384 bytes |
| $7BF0–$93FF | the car (one chapter), which a fight borrows | 6 KB |
| $9400–$CFFF | the overlay area: one of the three below at a time (BATTLE reaches down over the car) | 15 KB |
| $E000–$EDE0 | the picture, in the RAM under the KERNAL ROM; in a fight, the battle screen's characters ($E000) and screen ($E800) | 3.5 KB |
| $F000–$FCFF | in a fight, the sprite shapes, under the KERNAL ROM too | 3.3 KB |

| Overlay | File | Holds | Loaded when |
|---|---|---|---|
| LOAD | `ovl1` | checking the depot, and each car as it loads; the Deep Yards' picks and maps ([deep-yards.md](deep-yards.md)) | the Departure opens; a new chapter starts; a pick or a yard's fight |
| PASS | `ovl2` | the boarding desk, Passports, passes, Travel Stamps, saving and resuming, the receipt, and their buffers (`OVL2BSS`) | boarding; a save; a resume; the end of the trip |
| BATTLE | `ovl3` | the battle engine, the combat rules, the battle screen (`client/tactics.c`, `fe/c64/scene.c`, `fe/c64/sprites.s`) | a fight |

The memory map is `fe/c64/apb.cfg`, from cc65's own overlay map, with fixes that
matter: the main program ends where the car starts, because cc65 puts the C stack at
the end of the main program, and the stack must not grow into the car or an overlay; the
BATTLE overlay, 21 KB, is bigger than the overlay area, so it starts lower, over the car,
and the VM loads the chapter again after every fight (`APB_FIGHT_BORROWS_CAR`); and each
overlay keeps its constants in a segment of its own (`OVLnDATA`), because cc65 puts a
function's `static const` data right after the function's label when code and constants
share a segment. The PASS overlay's buffers (the desk's typed lines, the Passport's bits,
about 1 KB) live in the overlay too (`OVL2BSS`), not in the main program: they're used
only while it's loaded, never zeroed, and gone when another overlay comes in; so does
the save buffer. The fight's C is built with its locals static (`-Cl`: nothing in a fight
is recursive), which makes it about 800 bytes smaller.

**The rule for code:** before calling into an overlay, ask for it: `APB_NEED(APB_OVL_...)`
(`hal/apb_hal.h`), which loads it unless it's already there. Everywhere but the C64 it's
nothing. An overlay must never call into another one: they all load at the same
address, so the call would land in whatever is loaded there. The linker can't tell, so
`fe/c64/check_overlays.py` reads the linker's debug file and refuses any use of one
overlay's code or data from another (this is how a misplaced `enc_tile` was caught).
Which file goes where is in the Makefile (`C64_MAIN`, `C64_PASS`, `C64_BATTLE`), and
parts of `vm/vm.c` go to an overlay through `#pragma code-name` blocks.

**A chapter is at most 6 KB** (the compiler's limit for every machine, so a Departure
that compiles runs everywhere). The Fare's largest is 3.3 KB; *Eighteen Minutes*' is 3.7 KB.

## The disk

`tools/d64.py` writes 1541 images (and reads them back). The Fare's disk:

| File | Type | What |
|---|---|---|
| `apb` | PRG | the program |
| `ovl1`, `ovl2`, `ovl3` | PRG | the overlays, loaded at $9400 (`ovl3` at $7BF0) |
| `btab`, `bchr`, `bspr` | PRG | the battle graphics (`tools/battlegfx.py --c64`): their tables, the characters ($E000), the sprite shapes ($F000), loaded for every fight |
| `DEPOT`, `CAR00`, `CAR01`, ... | SEQ | the Departure, as `qsc.py build --split` writes it |
| `SAVE` | SEQ | a saved trip, written by the game |

File names are PETSCII the way cc65 stores C strings and c1541 stores names: lower case
letters as $41–$5A, capitals as $C1–$DA. So the VM's `"CAR00"` is found on the disk, and
`LOAD"APB",8` typed on a C64 finds `apb`.

## On the screen

| Rows | What |
|---|---|
| 0 | the status bar: "Kestrel  Lvl 1  HP 27/27  Debt 0", in reverse |
| 1–12 | the picture, once the story has shown one |
| 13–24 | the text window (rows 1–24 before the first picture, and during a fight) |

Text is written straight into screen memory, in upper and lower case, word-wrapped at 40
columns, at the bottom of the text window, which scrolls up a row at a time. Only the
window scrolls, so the picture's colours and the status bar stay put. It waits with
**-- more --** before anything scrolls off unread (with a picture up, that's every 11
lines: long passages page). Game text is ASCII, and
`fe/c64/c64.c` turns it into PETSCII; the client's own messages are C strings, which
cc65 has already made PETSCII. The C64 has no `~`, `_` or braces, so they show as `-`.
The status line, check results and the receipt are shared with the terminal
(`client/view.c`, `client/receipt_view.c`): ASCII lines that each front end prints its own
way, so both say exactly the same thing.

## The battle screen

A fight has the whole screen, Gold Box style: the map in tiles, three characters a
square, nine squares by five at a time, scrolling to follow the action; every fighter a
figure of two sprites, a multicolour body and a black outline over it; the roster beside
the map, what happened under it, and the command bar at the bottom: **Move Aim Guard Wait
Flee Quick Done**. It's `client/tactics.c`, shared with the desktop and the browser, on a
small HAL (`client/apb_scene.h`); the sentences are the terminal's (`client/battle_text.c`).

The C64 side is `fe/c64/scene.c`. The screen is the VIC-II's multicolour character mode in
bank 3: its characters (the frames, a bold font and the tiles, `tools/battlegfx.py`) at
$E000 and the screen at $E800, where the picture usually is, and the sprite shapes at
$F000, all in the RAM under the KERNAL. The figures need more than the VIC's eight
sprites, so every time the screen changes, `scene.c` plans the frame: the sprites sorted
down the screen, each given one of the eight that has finished drawing its last at least
3 raster lines above (the cursor and effects first, then bodies, then outlines; one that
can't be fitted waits a frame). The raster interrupt in `fe/c64/sprites.s` puts the first
eight up under the screen, at line 250, then moves each of the eight down the screen as
its last sprite finishes; it also runs the KERNAL's keyboard scan, the clock and the
sound effects, once a frame. The SID's first voice plays steps, swings, shots, hits,
misses, a fall, a blip and a buzz.

Keys: the cursor keys or the keypad digits (1-9) move; Return or space chooses; DEL,
RUN/STOP or the left arrow goes back; a command's first letter does it at once. A
joystick in port 2 does the same: its directions (diagonals too, repeating when held) and
its button.

When the fight ends, the story's screen comes back as it was (the text at $0400 was never
touched), with its colours, and the picture is loaded again.

## Pictures

A picture is 160 x 96 multicolour pixels on rows 1-12 (each pixel twice as wide as it is
tall): 40 x 12 cells of 4 x 8, each cell with three colours shared by the whole picture
and one of its own from the first eight (the C64's multicolour character mode). They
live in the 8 KB of RAM under the KERNAL ROM at $E000, the one place there's room. The
VIC (in bank 3) can show that RAM, and LOAD can write it, as writes always reach the RAM
under a ROM; only reading it back needs the ROM switched out for a moment
(`fe/c64/split.s`, `pic_show`, which copies each cell's colour to colour RAM).

A raster interrupt (`fe/c64/split.s`) switches the VIC twice a frame: to bank 3, the
picture's characters and multicolour just before row 1, and back to the text screen and
the ROM's characters just before row 13. It runs the KERNAL's own interrupt (keyboard,
cursor, clock) once a frame, in place of the CIA timer.

**Making them.** Draw a 160 x 96 PNG in the C64's colours and put it in the Departure's
`pictures/` folder, named like its `~ picture` (`platform_bench.png`).
`tools/c64pic.py` does the rest when the disk is built: it picks the shared colours and
each cell's own, maps every pixel to the nearest it can use, and shares characters
between cells that come out the same (at most 256; past that, the rarest are drawn with
the nearest one kept). `tools/c64pic.py render` shows what the C64 will show. On the
disk they're `pic00`, `pic01`, ..., numbered as the Departure lists them; a picture with
no PNG just leaves the last one up.

**Art from anywhere.** `tools/c64fit.py IN OUT.png` fits any picture (a drawing, a photo,
an image model's) to these rules: it cuts it to 10:3, scales it to 160 x 96, tries every
three of the colours it uses most for the shared ones, gives each cell the own colour
that suits it, and dithers between each pixel's nearest two. What comes out shows
unchanged. (`tools/c64pic.py` shares the three colours used most, unless they leave a
cell with two of its own; then the first three that fit.)

**The pictures we have.** Three of The Fare's (the Static, the concourse, the
Stationmaster) were drawn by Gemini from the prompts in [art-prompts.md](art-prompts.md):
the originals are in `pictures/gemini/`, and `paint.py` fits them with `c64fit.py`. The
rest are painted in code, with `tools/paint.py`: shapes, ordered dithering and a small
font for signs. Each Departure's `pictures/paint.py` writes its PNGs, and checks every one
comes through the C64's rules unchanged. Each picture is
planned in three shared colours (its background and two more) plus one of the first
eight per cell, as the comment above it says. A few things that learning cost:
- **Plan the shared three.** The converter shares the three colours used most, so a
  picture keeps a non-primary colour (grey, brown, orange, the light shades) only if
  it's among them. Rust-red that outweighs the grey, and the grey loses its place.
- **One colour of its own per cell.** Stars beside a red sun, frost on a cyan vault,
  white letters on a red board: two own colours meeting in a 4 x 8 cell. `resolve`
  clears the lesser one, or the drawing moves a few pixels.
- **There's no skin colour among the first eight.** People are seen from behind, lit
  yellow by a lamp, or in shadow.
- **Characters run out in noise.** Random scatter makes every cell different; static,
  rain and stars are built from a few repeating tiles.

## Testing without a C64

`make test-c64` plays the disk on a 6502 emulator (py65): the same machine code a C64
runs, loaded from the `.d64`. There are no ROMs: when the program calls the KERNAL,
`tests/c64/run_c64.py` answers in Python, from the disk image (the keyboard, the cursor,
OPEN, CHRIN, LOAD, ...), and stops loudly at any call it doesn't know. It types keys from
a choices file like the terminal's, and writes the transcript from screen memory: the
bottom row, each time the front end's `newline()` starts (its address comes from the
linker's debug file), with a line for each picture loaded. A fight's words come from
`hal_scene_log`, which shows nothing on a C64 but which the harness reads; there are no
interrupts here, so `scene_wait` (waiting for frames) is skipped, and each line of the
choices file is one key. `--shots DIR` saves a picture
of the whole screen (status bar, picture, text) each time it waits for a key, for a
person to look at; the C64's character ROM isn't there, so a stand-in font draws the
text. In a fight, it draws the battle screen as the VIC-II would (`tools/vic.py`): the
characters, colours and sprites from the C64's memory. The raster interrupt doesn't run in the emulator, so the shots show what it would
show.

- The Fare's edge route matches its reviewed transcript, and its Travel Stamp is the
  terminal's, symbol for symbol.
- A fight in the Lost Property office, a save to the disk, the machine switched off and
  on, the trip picked up from the disk and finished: the porter's hook won before the
  save is still on the receipt.
- All of *Eighteen Minutes*, from its own disk: the drone fight, the reactor, the first
  death, Dock 3 again; then the crew, the safe, MERIDIAN, and the last loop (the pods
  launched, the seeds taken, MERIDIAN let go), and the seeds handed to the
  Stationmaster.
- The Deep Yards, from its own disk: a yard number typed at the desk, floor 1's map
  built in the LOAD overlay and fought on quick, floor 2, and back up. The desktop and the
  browser play the same yard to the same transcript (`make test-modern`).
- No overlay reaches into another (`check_overlays.py`), and nothing passes 40 columns.

What it doesn't prove: timing, the real KERNAL and the real drive. That's VICE's job, on
your machine (Ubuntu's VICE package comes without the C64's ROMs, so CI can't boot it).

## Not yet

- **More art.** Most pictures are still painted in code. Kepler-Nine's and the Deep
  Yards' could be drawn from [art-prompts.md](art-prompts.md) too, and an artist could do
  more with the same 160 x 96 and the same rules.
- **The picture after a resume.** A save doesn't say which picture was up, so a trip
  picked up from the disk shows none until the story shows the next one.
- **Speed on a 1541.** The game is made for an SD2IEC (or JiffyDOS, or VICE's warp
  mode). On a stock 1541, at about 400 bytes a second, a fight takes most of a minute to
  load: the BATTLE overlay, its graphics, and the chapter again after.
- **Several Departures on a disk**, and a disk for each side of a long one.
